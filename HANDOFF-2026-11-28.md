### #66 — the PUSH scenario is real in Real mode
- **Why:** the PUSH scenario ("PUSH: $150 approved with a PingID push on the phone") always used the in-page mock phone (`MockPushModal`, `server/src/push.js`), so it never reached a real device. The owner wanted it real, with the device picker.
- **Now:** when the PingOne worker is configured, `PushModal` (in `web/src/components/PolicyGate.jsx`) asks `/api/mfa/real-otp/status` and, if configured, renders the same real flow as the MFA beat (`MfaModal`): picker (PINGID_MOBILE, SMS, EMAIL), PingOne sends the code or push, the typed code is checked by PingOne. Mock mode is unchanged.
- **Credit kind:** the PUSH retry claims a `push` credit, the MFA retry claims `stepUp`. `POST /api/mfa/real-otp/verify` takes an optional `method: "pingid-push"` and mints `push` in that case.
- **Test:** `App.test.jsx` "PingID push step-up (real, when the PingOne worker is configured)".

### #70 — approving the PingID push in the app completes the beat
- **Why:** this tenant's PingID push is approve-only (no number matching). The lab only completed from a typed code, so an approved push never finished the beat.
- **PingOne behaviour (measured live):** after `device.select` on PINGID_MOBILE the challenge is `PUSH_CONFIRMATION_REQUIRED` (links `otp.check` and `cancel.push` are present); when the approver taps Approve it becomes `COMPLETED` within a few seconds.
- **Lab:** `pingoneOtp.select()` returns `push: true` for that status; new `pingoneOtp.poll()` reads `GET /deviceAuthentications/{id}` (`pending`, `approved` once and the challenge ends, or `failed` on FAILED/EXPIRED); new route `GET /api/mfa/real-otp/poll?method=pingid-push` mints the credit (`push` for the PUSH beat, `stepUp` for MFA). `MfaModal` polls every 2 s after a push pick and carries on by itself; the code box stays as the fallback and SMS/EMAIL are never polled.
- **Tests:** server `pingone-otp.test.js` (pending then approved once; failed or expired and non-push cannot be polled), web `App.test.jsx` "PingID push approve".
- **Bug the browser run caught that the tests missed:** the `select` route did not return `push`, so the page never polled. There is still no route-level server test for the real-OTP routes; add one if the routes change again.

## Findings about PingID push (so nobody re-investigates)

- A real run of the MFA beat picking PINGID_MOBILE: PingOne accepted the selection and the device record showed a push failure (`pushFails`) exactly 60 s after each of two selections. That reads as an unanswered or undelivered push, not a rejection.
- A third attempt arrived on the phone, was answered, and logged no failure. **Correction:** an earlier note here said the app showed a number to type. The owner confirmed number matching is not on: the push is approve-only (see #70). The app's own passcode view still works as a fallback (OTP is enabled on the device).
- Pushes are intermittent from the lab's side: two went unanswered or undelivered, later ones arrived instantly. Stale pushes from earlier attempts stay on the phone until they time out, so approve only the newest.
- SMS through the picker worked end to end in the browser.
- Read the device with the worker token: `GET .../deviceAuthentications` (open) lists devices with `pushStatus`, `otpStatus`, `pushFails`, `notification`. Opening a challenge sends nothing; selecting a device does.

## How to work on this lab (what cost time this session)

- **A challenge opened through the API is not attached to the browser modal.** Opening the MFA modal cancels it and starts a new one at the picker. Run the real flows from the page (Playwright against the proxy hostname works; the script waits for the owner's tap).
- **Test a change on a separate copy, not the owner's running lab:** in a worktree, copy the lab `.env` in (git-ignored), `HOST_PORT=7685 docker compose -p hmlab-verify up --build -d`, drive it with Playwright, then `docker compose -p hmlab-verify down --rmi local` and delete the copied `.env`. Opening a challenge is free; selecting a device pings the owner's phone, so ask first.
- **Story steps that need a modal** (`mfa_video`) are skipped when the modal is not open. To reproduce a bubble over the modal, open the modal first, then switch Story on. The modal covers the header's Story toggle at 1800 px, so click it by script.
- **Never recreate `lab-proxy` with plain `docker compose up`.** It drops the labs' networks and every lab 502s until they are re-attached. Use `shared/lab-proxy/reload.sh`. A lab that answers 502 right after is usually just not running (e.g. privilege-demo).
- **demo-shelf:** `docker compose up` fails on missing variables. Use `SHELF_OPEN=0 npm run docker` in `standalone/demo-shelf-LAB` (it otherwise opens a browser).
- **Heavy work goes to the Air** (`air-test`); it was unreachable, so tests ran locally after `npm ci` in `web/` and `server/` of the worktree.
- Local `main` in the AI-DEMO-Standalone checkout is held by another worktree with uncommitted changes, so it was fetched, not moved.
